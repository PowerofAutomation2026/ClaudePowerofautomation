The problem with "an agent that runs Terraform"

Asking a chat assistant for a database is a great experience. Giving a language model Contributor rights is not. Models can be talked into things - by a user, by a document, by text hidden in a resource name.

💬

"The user said yes"

If confirmation happens in the chat, the model decides whether it happened. A prompt injection can simply claim it did.

🔑

One identity does everything

The process that reads untrusted text is usually the same one holding write access to your subscription.

🧾

Plans nobody can read

A Terraform plan is written for engineers. Approvers click "OK" on a summary the model improvised.

How it works: three parts, two identities, one human

The agent proposes. A read-only service plans and explains. A person approves on a separate page. Only then does a different identity touch Azure.

What a hijacked agent can still do

Read what its user may read, create plans, and ask for approvals. It can also trip the server's automatic freeze - an intentional fail-closed.

What it cannot do

Approve, apply, destroy, raise its own rights, remove a lock, or make the executor apply a plan that differs from what the approver saw.

What makes it different

Every item below is enforced by the server or by Azure itself - never by the agent's instructions.

🧍

Out-of-band approval

No approve tool exists. Decisions happen on a separate page with a different token audience and a fresh sign-in; valid 30 minutes, usable once.

🪪

Split identities

The agent-facing service is read-only. A second service with a custom role (no role assignments, no lock removal) applies approved plans.

🛡️

Policy gate on the plan

Regions, tags, public access, TLS, SKUs, protected resources and blast radius are checked on Terraform's own plan - again at approval and at apply.

💶

Cost before apply

A labelled monthly estimate from Azure's public list prices, with an optional budget cap that blocks the apply.

⏳

Time-boxed environments

"For 8 hours" creates a deployment that gives notice and then removes itself. Only deployments created that way are ever touched.

🧭

Drift and rollback

Ask whether Azure still matches what was deployed, on demand or nightly. Plan a return to the previous applied inputs.

🗣️

Explain this plan

The server writes the plain-English summary, risk level and next step - the model reads it out instead of inventing one.

🧯

Kill switch

Admins freeze all changes out of band. Bursts of denied calls, destroy attempts or plans freeze it automatically. Daily deletion quota.

📜

Per-user audit

Every call on both channels with the Entra identity, to Log Analytics and to write-once storage. Workbook, alerts and queries included.

Install: one double-click

On a Windows admin workstation, unzip the package and double-click Install.cmd. It installs what is missing, signs you in, runs preflight checks before changing anything, creates the Entra groups, deploys to Azure and prints a pass/fail summary with the one URL you paste into Copilot Studio.

Install.cmd

Check first, change nothing:

Install.cmd -PreflightOnly

Pipelines (no prompts):

pwsh ./Install-AzureTerraformMcp.ps1 -Unattended -ConfigFile ./install.config.json

Automated vs. needs a person

  • Prerequisites (Azure CLI, Power Platform CLI), sign-in, subscription and environment pickers
  • Preflight list with the exact fix for every failure
  • Four Entra groups, you as admin, an optional second approver
  • Azure deployment, custom roles, locks, app registrations
  • Solution and custom connector in your Power Platform environment
  • Creating the agent, adding the tool by pasting the server URL (Dynamic discovery) and publishing it in Copilot Studio
  • Pasting values and the client secret - only if you need the manual fallback
  • Each user's first sign-in to the connection; licensing; admin consent if you lack the role

Step by step

See what would fail before anything is created.
  1. Run Install.cmd -PreflightOnly.
  2. Read the PASS / WARN / FAIL list: subscription role, Entra permissions, region, name availability, Power Platform environment, data-loss-prevention hints.
  3. Each FAIL line names the fix. Apply it and run again.
Run the installer and answer five questions.
  1. Double-click Install.cmd. Pick the subscription and the Power Platform environment from the lists.
  2. Keep "plan-only" for the first run.
  3. Wait for the green INSTALLED banner; the summary is in out/install-summary.md.
  4. If it stops, fix what it says and run it again - finished steps are skipped.
Connect the agent by pasting one URL.
  1. Agent › Tools › Add a tool › New tool › Model Context Protocol.
  2. Server URL: https://<your-mcp-host>/mcp (printed by the installer).
  3. Authentication: OAuth 2.0 › Dynamic discovery. Create.
  4. Create new connection and sign in with your own account.
  5. Add to agent, paste agent-instructions.md, publish, share with the requester and viewer groups.

No client id, no secret, no endpoint URLs: the server publishes its own OAuth metadata. Not verified against a real Copilot Studio wizard - if yours has no "Dynamic discovery" option, use the fallback tab.

If the wizard has no "Dynamic discovery" option, or it fails.
  1. Open the FALLBACK section of out/copilot-studio-wizard-values.md.
  2. In the same wizard choose OAuth 2.0 › Manual and paste the values (client id, the secret from out/connector-client-secret.txt, three URLs, scopes).
  3. Create the connection and sign in. Same server, nothing to reinstall.

Prefer Easy Auth in front of the MCP endpoint? Deploy with -ConnectorAuth manual; the discovery endpoints are then switched off.

Tell approvers where decisions happen.
  1. Send them the approval page address from the summary.
  2. Add a Conditional Access policy for the approval app: multi-factor, sign-in every time.
  3. Add at least one other person to the Approvers group - the two-person rule needs two people.

Security questions people ask

What if the agent is prompt-injected and "confirms" for the user?

Nothing happens. There is no tool that approves, and the apply tool is refused unless a human created an approval on the separate page for that exact plan file. Chat content is not an input to that decision.

What if someone steals a user's token for the MCP?

It works for reading and planning as that user until it expires. It is rejected by the approval service (different audience, client and scope), so nothing can be applied with it.

What if the agent-facing container itself is compromised?

It holds a read-only Azure role. It could forge its own records, so the executor ignores them: it reads approvals from a store that container cannot write, asks Terraform what the plan file really does, and compares that with what the approver saw. It can read Terraform state - that is a real residual risk.

The server has public sign-in endpoints now. Is that a hole?

For "Dynamic discovery" the MCP front-end serves OAuth metadata plus register, authorize and token endpoints without authentication - that is how discovery works. They create nothing and issue nothing themselves: registration returns the one existing client and never a secret, authorize only redirects to your tenant's Entra sign-in, token only forwards to Entra. Redirect addresses must match an exact allow-list, PKCE is required, and requests are rate limited. The trade-off: in this mode the platform's own authentication layer no longer sits in front of the MCP endpoint; the server's token validation does that job alone. A manual mode keeps the old setup.

Can an approved plan delete production data?

In locked environments the apply role cannot delete data-bearing resource types, the resource group carries a delete lock, protected deployments are refused, and a daily deletion quota applies. An Owner can still remove those protections on purpose; an alert fires when a lock or role changes.

So it cannot be hacked?

No system can promise that. A person can approve the wrong thing, two insiders can collude, and everything here still has to be confirmed in a real tenant. The threat model lists each scenario with what stops it and what remains.

What is tested - and what is not

Verified locally
  • Automated test suite for policy, cost, approvals, roles, limits, injection inputs, redaction, durability and token budgets (count in the README)
  • Both HTTP channels with locally signed tokens: wrong audience, wrong client, stale sign-in and replays are rejected
  • terraform validate for all 15 templates with the pinned provider
  • Installer and deploy scripts executed end to end in PowerShell 7 against fake az and pac command-line tools
  • The whole "Dynamic discovery" path on the real server locally: challenge, metadata, registration, authorize redirect, token exchange against a stub identity provider, then MCP calls
  • This page: rendered at desktop and phone widths, light and dark
Not verified
  • Anything against live Azure, Entra ID, Power Platform or Copilot Studio
  • Install.cmd itself (no Windows machine was available) and winget installs
  • Real token claims, custom-role, lock and policy behaviour
  • The approval page's browser sign-in flow
  • Copilot Studio's real "Dynamic discovery" wizard (which MCP authorization revision it follows, whether it insists on a client secret) - the reason a manual fallback stays
  • Connector and solution creation through the real Power Platform CLI and Dataverse API
  • The container image build

Run it in a sandbox subscription first and expect to adjust small things.
